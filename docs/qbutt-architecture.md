# qbutt
## Архитектура и план реализации

**Редакция:** 0.1, 12 сентября 2026 года.  
**Статус:** проектное решение по результатам исследования публичных исходников и документации. Это не отчёт о собранном или протестированном прототипе.  
**Основная платформа:** Windows x64. Linux используется также для сервера и воспроизводимых сетевых испытаний.

## 1. Продукт и границы

qbutt сохраняет удобство нативного qBittorrent, но получает две центральные возможности:

1. **Smart Repair / Update:** находит подходящие локальные данные, проверяет их относительно новой раздачи, докачивает недостающее и корректно обрабатывает переименования, изменённые размеры и восстановление после сбоя.
2. **Swarm Paths:** один торрент загружается через несколько явно управляемых сетевых выходов: домашнюю сеть и собственные VPS. Выбор маршрута учитывает доступность и полезную отдачу, а не только ping.

Сопутствующие возможности первого продуктового релиза: понятные правила завершения и удаления, объяснимая диагностика, подписанное обновление, отдельный профиль, отзывчивый Qt-интерфейс. Потоковое воспроизведение и объединение источников одинаковых файлов между раздачами допускаются следующими независимыми модулями.

Критерий изменения любого слоя: конкретная пользовательская выгода и проверяемый результат. Форки qBittorrent, libtorrent, Mihomo и серверных компонентов допустимы. Совместимость старых внутренних API не является целью. Сохранность данных, протокольная корректность и ясное поведение остаются требованиями.

### Не включать в начальный объём

- Новый BitTorrent-движок, TCP/QUIC-стек или собственную криптографию.
- Удалённых торрент-работников с собственными piece picker и распределённым хранилищем.
- Глобальное хранилище копий всех когда-либо загруженных кусков.
- Автоматическое сканирование всего диска и всего DHT.
- Универсальный плагинный маркетплейс, встроенный LLM и переезд UI на Electron.
- Постоянные четыре соединения к одному и тому же пиру с разными идентичностями ради получения дополнительных upload slots.
- Автоматические баны «жадных» клиентов по названию или отсутствию скорости.
- Полную замену WebUI, RSS и поисковой системы до появления отдельной доказанной необходимости.

### 2.1. Имеющиеся строительные блоки

| Источник | Что уже есть | Решение для qbutt |
|---|---|---|
| libtorrent `truncate_files` | Обрезание файлов, размер которых больше значения в `file_storage`; функция присутствует и в ветке 2.0 | Использовать под контролем RepairService, не писать собственный платформенный truncate без причины. [S01] |
| libtorrent `resolve_links` | Сопоставление одинаковых файлов; для v1 есть ограничения на размер pieces и выравнивание, для v2 используются корни файлов | Переиспользовать проверенные случаи и тесты, расширить поиск кандидатов. Это не универсальный binary patcher. [S02] |
| libtorrent multi-homing | Несколько listen contexts, связанные UDP-сокеты, DHT и tracker endpoints | Расширить модель до явных путей через разные прокси вместо нескольких независимых клиентов. [S03] |
| libtorrent `instantiate_connection` | Фабрика соединений уже принимает настройки прокси | Распространить выбранный PathContext до фабрики и смежных UDP/tracker компонентов. Это точка входа, не весь необходимый патч. [S04] |

| Mihomo adapters | `DialContext`, `ListenPacketContext`, признаки возможностей адаптера | Добавить необходимую телеметрию и управляемый жизненный цикл вокруг существующих реализаций. [S08] |
| BiglyBT Swarm Merging | Объединение источников одинакового файла из разных раздач | Архитектурный референс для следующего этапа, не Java-зависимость в qbutt. [S09] |
| autotorrent2 | Поиск и сопоставление локальных данных с torrent metadata | Алгоритмический референс и набор сценариев поиска, не обязательный Python runtime. [S10] |
| cross-seed | Сопоставление похожих раздач, связывание файлов и recheck, включая частичные совпадения | Взять UX и тестовые случаи; не смешивать cross-seeding с патчами произвольной версии игры. [S11, S12] |

| WinSparkle | Windows updater с подписанными обновлениями | Первый кандидат для установленной версии; portable обновление требует отдельной проверки сценария. [S14] |
| libtorrent simulation/fuzzing, torrenttools | Сетевые сценарии, fuzzing и генерация torrent fixtures | Использовать в CI вместо набора только happy-path тестов. [S15, S16, S17] |
| FRP | Обратное проксирование и доставка исходного адреса при поддержке принимающей стороны | Референс/инструмент для проверки inbound; не считать простой проброс порта полной BitTorrent-интеграцией. [S18] |

### 2.2. Поправки к исходной концепции

**Многомаршрутность не складывает физическую полосу одного домашнего подключения.** Все туннели по-прежнему проходят через него. Возможный выигрыш: другие маршруты, доступность других пиров, более подходящий выбор соединений и входящие подключения через VPS.

**Hysteria2 уже делает TCP-проксирование с отдельным TCP-соединением на серверной стороне.** Перенос всего BitTorrent-клиента на VPS не нужен только для того, чтобы TCP до пира заканчивался на VPS. BitTorrent-запросы и их очередь при проксировании всё ещё зависят от пути до дома, но это отдельная гипотеза для измерения. Удалённые workers пока не включаются. [S19]

**Несколько протоколов на S1 не означают несколько независимых сетевых выходов.** Они могут отличаться устойчивостью, стоимостью обработки и поведением congestion control, но делить внешний адрес и канал VPS.

**Найденные, доступные и активно отдающие пиры являются разными множествами.** Ноль байт в секунду не доказывает злонамеренность. Маршрутизация не должна наказывать пир за обычное состояние choking или отсутствие нужных запросов. Основное поведение BitTorrent сохраняется. [S03, S20]

**Существующий SOCKS UDP relay не равен публичному входящему порту.** `ListenPacketContext` у адаптера является интерфейсом UDP-проксирования. Возможности устойчивого внешнего mapping и приёма незапрошенных пакетов устанавливаются отдельной проверкой. [S08, S19]

**Отдельный процесс без TUN не гарантирует обход чужого системного TUN.** Сосуществование с Koala проверяется на реальном хосте для всех типов трафика.

### 2.3. Что пока неизвестно

Исходники пользовательских форков Mihomo/Xray и их точные revision не предоставлены. Скриншот подтверждает используемые имена узлов и транспортов, но не доказывает их внутренние API, возможности обратного listen, сохранение UDP mapping или доступность расширенной телеметрии. Первый этап реализации должен сформировать capability report из реальных сборок, а не предположений по upstream.

## 3. Компоненты

```text
qbutt.exe
  Qt UI
  Application services
    TorrentLifecycle
    RepairService
    PolicyService
    NetworkPolicy
    PathRegistry / RouteSelector
    Diagnostics
    UpdateManager
  libtorrent-qbutt
    одна session
    отдельный стандартный piece picker каждого торрента
    peer pool каждого торрента
    PathContext в сетевых операциях
    один владелец записи каждого набора файлов
        |
        +--> Native backend --> физический интерфейс
        |
        +--> Proxy backend --> qbutt-net.exe
                                  |
                                  +--> S1 / выбранный transport
                                  +--> S2 / выбранный transport
                                  +--> S3 / выбранный transport

VPS: существующие транспортные серверы
     + опциональный qbutt-edge для полноценного inbound
```

### 3.1. qbutt.exe

Нативное приложение на существующем Qt UI и модели qBittorrent. Не переносить очереди, файловые приоритеты, RSS, категории и session state в новый backend только ради новой архитектурной картинки.

Application services принимают пользовательские решения и управляют долгими операциями. Низкоуровневый сетевой код и piece scheduling остаются в libtorrent. Решения, требующие состояния конкретного peer connection, выполняются в правильном контексте движка, а не через GUI polling.

### 3.2. libtorrent-qbutt

Один поддерживаемый набор API/ABI. Не сохранять ветвления для libtorrent 1.2. Основной fork расширяется следующими сущностями:

- PathContext: выбранный сетевой выход и поколение его состояния.
- ProxyContext: способ открыть TCP/UDP именно через этот путь.
- Route-aware tracker, DHT, peer и webseed operations.
- Trusted accepted-connection metadata для remote inbound.
- Repair integration: безопасная постановка данных, отображение путей и владение записью.

Не заменять rarest-first, endgame и стандартную проверку pieces собственным глобальным планировщиком. Многомаршрутность выбирает транспорт для соединения; выбор блоков остаётся общим для всех соединений этого торрента.

### 3.3. qbutt-net.exe

Отдельный поставляемый вместе с приложением процесс на базе пользовательского Mihomo fork. Не CGO-библиотека внутри C++-процесса.

Он отвечает за жизненный цикл туннелей, локальные listeners, выбор transport variant внутри edge, DNS/bootstrap, привязку исходящих сокетов и транспортную телеметрию. Он не знает piece hashes, пути игр, категории торрентов и правила удаления.

В обычном режиме без VPN qbutt может работать без qbutt-net. При падении qbutt-net проксированные соединения теряются, но приложение и файловый журнал остаются живы.

### 3.4. qbutt-edge

Опциональный небольшой серверный агент, не торрент-клиент. Нужен для выдачи публичных TCP/UDP endpoints, доставки входящих соединений, сохранения настоящего remote endpoint и проверки доступности.

Сначала использовать существующие транспортные серверы без модификации. Добавление qbutt-edge не должно требовать переезда всех клиентов сервиса «Свои сети» на новую серверную сборку.

## 4. База, репозитории, состояния

### 4.1. Выбор исходной базы

Контрольная стабильная база на дату исследования: qBittorrent 5.2.3 и зафиксированная совместимая ревизия libtorrent 2.0.x, используемая для контрольной сборки. В публичных релизах уже есть libtorrent 2.1.1, а qBittorrent 5.3 beta использует ветку 2.1. Переход допустим отдельным изменением, но не должен незаметно совпасть с первым multipath-патчем и лишить нас корректного сравнения. [S21, S22]

Первый PR обязан записать реальные commit SHA, compiler, Qt, OpenSSL, Boost и Go в lock manifest. Приведённые здесь названия веток являются исследовательскими ссылками, не заменой lockfile.

### 4.2. Организация workspace

```text
qbutt/
  app/                 fork qBittorrent
  deps/libtorrent/     fork libtorrent, pinned revision
  net/                 fork Mihomo / qbutt-net entrypoint
  edge/                optional reverse gateway
  contracts/           IPC schemas, semantic definitions
  tests/fixtures/      torrents and generated data, no copyrighted game dumps
  tests/network-lab/   namespaces, path shaping, mock peers and trackers
  tests/repair/        crash, layouts, truncation, rollback
  docs/adr/            architectural decisions
  upstream-lock.json
  build/
```

Это описание логического workspace. Необязательно физически переносить все upstream-файлы в один Git repository: submodules или workspace manifest допустимы. Каждый компонент должен собираться отдельно и иметь тестовый контракт.

### 4.3. Данные приложения

Отдельный профиль qbutt. Импорт из qBittorrent является копированием настроек/metadata, не общим live-профилем. Перед активной записью в импортированные данные исходный клиент должен перестать ими управлять.

Существующий механизм resume данных qBittorrent сохраняется. Новый небольшой `qbutt.db` используется только для собственных настроек, маршрутов, политик и repair journal; не дублирует каждую структуру session.

Секреты не попадают в Git, diagnostic export или обычные журналы. Импорт сетевых профилей выбирает только необходимые nodes/providers, не переносит автоматически Koala TUN, глобальные правила и весь системный DNS-конфиг.

## 5. Swarm Paths: модель

### 5.1. Три разных понятия

**Edge**: логическое присутствие в сети, например Native, S1, S2, S3.  
**Transport**: способ добраться до edge, например Hysteria2 Gecko, Hysteria2 Salamander, ShadowQUIC v2 JLS или VLESS.  
**Path**: конкретное пригодное для операций сочетание edge, transport, address family и поколения состояния.

Начальное поведение: один активный transport на edge и резервные варианты. При необходимости допускается временный второй transport для испытания или переключения без немедленного обрыва здоровых соединений. DHT и tracker identity не размножаются только из-за количества пунктов подписки на одном VPS.

```text
Edge S2
  transports:
    hysteria2-gecko
    shadowquic-v2-jls
    vless
  current_transport: hysteria2-gecko
  public_ipv4: verified-or-unknown
  public_ipv6: verified-or-unavailable
  capabilities:
    tcp_dial
    udp_relay
    stable_udp_mapping
    tcp_inbound
    udp_inbound
```

Внешний IP и port нельзя определять по результату случайного `curl`, который мог уйти через Koala. Они принадлежат конкретному PathContext и подтверждаются соответствующим транспортом/проверкой.

### 5.2. Контракты управления и передачи данных

**Управление:** versioned IPC по named pipe на Windows, local socket на Linux. Первоначально достаточно небольших сообщений с сериализацией JSON и ограничением размера. Нет необходимости вводить gRPC, service discovery и отдельный message broker.

Предлагаемые операции, которых нельзя считать существующим upstream API:

```text
Hello(protocol_version, capabilities)
ListEdges()
ActivateTransport(edge_id, transport_id)
DescribePath(path_id, generation)
ObservePath(path_id, generation)
ClosePath(path_id, generation)
SubscribeEvents()

Позднее для inbound:
AcquireListener(edge_id, tcp_or_udp, requested_port, lease)
RenewListener(listener_id)
ReleaseListener(listener_id)
```

**Данные:** сначала существующий SOCKS5 TCP и UDP ASSOCIATE по отдельному loopback listener на path/edge. Локальный listener закреплён за конкретным proxy adapter, не за автоматически перескакивающей группой с другими VPS. При измеримом ограничении данного транспорта допускается замена внутреннего data-plane на более прямой IPC/backend, но это не предварительное условие. [S06, S07]

Сырые bytes не передаются JSON/base64. Управление и длинные потоки данных не должны блокировать друг друга. Все очереди ограничены; прекращение чтения должно создавать backpressure.

Listeners открываются только на loopback с случайными ephemeral credentials либо эквивалентным ограничением локального доступа. Control IPC имеет ограничения доступа текущего пользователя. Весь интернет не получает новый неаутентифицированный прокси.

### 5.3. Область патча libtorrent

Фабрика `instantiate_connection` уже получает proxy settings, поэтому TCP spike может быть небольшим. Полноценная функция требует большего: [S04]

1. Передать PathContext через выбор peer connection и асинхронный connect.
2. Убрать предположение, что один session-global proxy описывает все пути.
3. Обеспечить отдельные устойчивые UDP associations, DHT/listen contexts и uTP managers там, где этого требует адресация.
4. Привязать HTTP/HTTPS trackers, UDP trackers, DNS и webseeds к выбранной политике пути.
5. Сохранить оригинальные адреса пиров для фильтров, счётчиков, deduplication и логов; localhost SOCKS не является адресом пира.
6. Учитывать все собственные public endpoints для защиты от self-connections.
7. Для inbound получать peer endpoint и path от доверенного gateway, а не из произвольного BitTorrent payload.

TCP-only spike должен быть явно экспериментальным. Он не имеет права заявлять tunnel-only защиту, пока DHT, UDP, DNS, trackers, webseeds и переходы политик не прошли отдельные тесты.

### 5.4. Discovery и идентичность

Общая база пиров существует **внутри конкретного torrent/infohash**, а не как разрешение соединяться с любым известным IP в любом рое.

```text
PeerCandidate
  torrent_key
  endpoint
  discovered_via[]
  allowed_source_scope
  path_observations[]
  last_seen
  expiry
```

DHT-контекст привязывается к фактическому внешнему пути; смена IP требует обновления соответствующей идентичности и состояния. Это существенно для BEP42. Входящая достижимость и роль read-only/NAT-limited DHT учитываются отдельно. [S23]

Для публичных tracker announces сохраняется поведение multi-homing, описанное BEP7: реальные исходящие адреса, согласованные peer identity/key и правильный port. Нельзя просто написать `announce_ip=S1` и считать задачу решённой. Tracker intervals и limits соблюдаются. Один клиент не должен изображать несколько независимых потребителей только ради более частых выборок. [S24]

Известный и проверенный публичный listener объявляется только с правильным адресом/портом. Outgoing-only path может использовать доступные способы поиска и исходящие соединения, но UI не должен представлять его вход как открытый. Для UDP отдельно проверяется длительность жизни mapping.

### 5.5. Политики сети

| Политика | Разрешённое поведение |
|---|---|
| Direct | Только физический/явно выбранный native путь |
| Pinned | Один выбранный edge, разрешённый fallback transport внутри того же edge |
| Mixed | Native и выбранные VPS одновременно; реальный домашний адрес сознательно участвует в рое |
| Tunnels only | Только выбранные remote edges; отсутствие работоспособного пути останавливает операции |

Для private torrents применяется консервативный Pinned policy, выключены DHT/PEX и сохраняются ограничения на источники пиров. Не расширять обнаружение за пределы разрешённого tracker scope. Если правила конкретного трекера требуют дополнительных ограничений, они имеют приоритет над ускорением. [S25]

Политика переключается транзакционно относительно соединений: запрещённые старые TCP/UDP sessions действительно закрываются. Изменение галочки, после которого час живёт старый DIRECT поток, не считается выполнением политики.

В Tunnels only не должно быть скрытого direct fallback для tracker DNS, metadata fetching, DHT, PEX-соединений, webseeds или проверки доступности. Для bootstrap адресов VPN-серверов нужна отдельная явная политика; она не является разрешением на прямой torrent discovery. Для обновлений приложения и иных control-сервисов их сеть показывается отдельно.

### 5.6. Сосуществование с Koala

qbutt-net не создаёт второй системный TUN. Внешние сокеты transport adapters и Native backend привязываются к выбранному физическому маршруту, насколько это поддерживает используемая платформа. Результат проверяется, а не предполагается по названию адаптера.

Испытания включают Koala off/on/restart, разные его режимы DNS и маршрутизации, IPv4/IPv6, изменение default route, отключение интерфейса и восстановление после сна.

Если конкретная конфигурация Koala всё равно перехватывает трафик qbutt-net, нужен явный вариант совместной настройки исключения. qbutt не редактирует Koala автоматически и не начинает молча строить двойной туннель. Диагностика сообщает фактический путь и необходимую настройку.

### 5.7. RouteSelector

Первый рабочий алгоритм не требует обучения нейросети или сложного contextual bandit.

- Исключить запрещённые и заведомо неработающие пути.
- На новом соединении учесть историю доступности и полезной передачи.
- Сохранить здоровое существующее соединение; не переподключать из-за маленького изменения ping.
- При реальном отказе попробовать другой path.
- Небольшую долю новых попыток использовать для исследования альтернатив.
- Иметь общий лимит соединений и попыток, а не отдельный полный лимит на каждый edge.

Предлагаемый стартовый экспериментальный budget: не более 10% новых dial attempts на exploration, с отдельно ограниченным общим числом конкурентных попыток. Это параметр лабораторной настройки, не установленный исследованиями оптимум.

Не сравнивать только `bytes/seconds` у idle/choked соединений. Отдельно хранить connection success, интервалы ожидания данных при outstanding requests, интервалы choking, время жизни соединения и полезные проверенные bytes. RTT до VPS не является RTT до пира, а ни один из них сам по себе не доказывает будущую скорость.

После успешного handshake остаётся не более одного обычного соединения к данному peer для данного торрента, с учётом штатного разрешения дубликатов. Переезд TCP выполняется переподключением, не выдуманной бесшовной миграцией существующего TCP.

Автоматический выбор протокола и выбор edge разведены. Не выдавать все 500 Мбит/с как независимый гарантированный bandwidth budget трём Hysteria-туннелям. Общий канал, очереди и fairness должны учитываться агрегированно. Возможности/алгоритм congestion control конкретного transport берутся из существующего ядра и проверяются стендом. [S19]

### 5.8. Inbound через VPS

Полноценная реализация состоит из четырёх частей:

1. Authenticated lease публичного listener на VPS.
2. Доставка входящих TCP streams/UDP datagrams домой через разрешённый транспорт.
3. Передача оригинального remote IP/port в доверенных внутренних metadata.
4. Правильная публикация listener и независимая внешняя проверка TCP и UDP.

Простой FRP-проброс теряет часть endpoint semantics, если принимающий код не понимает передаваемый original IP. PROXY protocol нельзя просто дописать перед BitTorrent handshake и ждать, что стандартный libtorrent его примет. При использовании FRP его заголовок разбирается собственным trusted adapter до создания peer connection. [S18]

Предлагаемая реализация qbutt-edge использует имеющиеся transport adapters, а не новый транспорт PC ↔ VPS:

- qbutt-net открывает через выбранный adapter управляющее соединение к qbutt-edge. Сервис доступен только по разрешённому внутреннему endpoint/ACL, с отдельной аутентификацией qbutt.
- qbutt-edge получает lease и открывает публичный listener. Он сообщает по control channel id принятого соединения и настоящий remote endpoint.
- Для каждого входящего TCP connection qbutt-net открывает отдельное соединение через тот же adapter к work endpoint qbutt-edge и привязывает его к принятому connection id. В Hysteria2 это использует существующие отдельные QUIC streams.
- qbutt-edge связывает work connection с принятым peer TCP socket. qbutt-net передаёт qbutt.exe raw stream и доверенные endpoint metadata через локальный accepted-connection adapter.
- Не пропускать весь peer data plane через одно упорядоченное control TCP connection. Отдельные потоки должны сохранять независимые очереди и backpressure.
- UDP использует capability `udp_relay`: небольшой ограниченный envelope для listener id, оригинального remote endpoint и payload внутри существующего datagram транспорта. Он связан с аутентифицированной lease; public UDP socket и его порт принадлежат qbutt-edge.
- Если datagram transport недоступен, UDP capability выключается. Нельзя незаметно заменить её UDP-over-TCP и продолжить показывать прежние свойства пути.

Это новый application-level reverse control contract, не новая криптография и не дополнительный QUIC. Конкретный framing и формат аутентификации фиксируются в contracts после проверки реальных adapters. FRP подходит для раннего диагностического прототипа и сравнения, но его ограничения по original endpoint и head-of-line blocking нельзя автоматически переносить в окончательный data plane.

Меры эксплуатации: отдельные credentials qbutt, ограниченный набор разрешённых публичных портов, лимит connections и буферов, lease timeout, аутентификация и отсутствие публичного административного API. Нет свободной функции «открой любой сокет сервера от имени любого клиента».

## 6. Smart Repair / Update

### 6.1. Пользовательские операции

**Докачать здесь:** исправить/докачать существующий каталог по одной `.torrent`; явно обработать oversized tails.  
**Найти мои данные:** искать кандидатов в выбранных каталогах и известных загрузках.  
**Обновить существующую установку:** сопоставить старую и новую структуру, подготовить новое содержимое и заменить целевые файлы по журналу.  
**Проверить без изменений:** только анализ, без truncate, перемещений, удаления и запуска загрузки.

Предварительный экран разделяет:

```text
Найдено кандидатов:        91 ГиБ
Подтверждено хэшами:       73 ГиБ
Нужно получить из сети:    18 ГиБ
Временное место на диске:  46 ГиБ
Изменяемые файлы:          12
Лишние хвосты:             3 файла
Неизвестные файлы:         не будут изменены
```

Числа являются примером интерфейса, не измерением. До полного анализа оценка подписана как предварительная. «Нашли похожие имена» нельзя выдавать за «переиспользуем 73 ГиБ».

### 6.2. Поиск кандидатов

Порядок от дешёвого к дорогому:

1. Ожидаемый путь в выбранном каталоге.
2. Известные переименования и file mappings существующих торрентов.
3. Размер, близкое имя и относительная структура выбранных каталогов.
4. Доступные v2 file roots/подходящие v1 piece metadata.
5. Хэширование содержимого для доказательства совпадений с целевой раздачей.

Метаданные и быстрые fingerprint служат индексом кандидатов, не окончательной проверкой. Индекс не хранит вторую копию payload. Изменение file identity/размера/mtime инвалидирует предположения; окончательная приёмка всё равно идёт через целевые хэши.

Пользователь выбирает области поиска. Не запускать background hashing всего компьютера после установки приложения.

### 6.3. Как проверять v1/v2

Для v1 целевой торрент задаёт логический поток файлов и границы pieces. Кусок может пересекать два файла. Сопоставление файла из другого каталога проверяется в **целевом расположении байтов**, а не по номеру piece из старой раздачи. Сдвиг расположения целого файла в новом torrent layout сам по себе не запрещает переиспользование его байтов. [S02, S26]

Для v2 используются per-file Merkle roots и соответствующая проверка дерева. Пустые файлы, pad files, hybrid layouts и последний неполный piece входят в тестовые fixtures. [S26]

Стандартные torrent hashes не дают дешёвого универсального поиска всех совпадающих подстрок старого архива после вставки байтов в его середину. Такой delta update требует дополнительных target signatures/metadata или ограниченных эвристик. zsync/librsync/casync интересны для отдельного publisher-assisted режима, но не являются волшебной заменой recheck обычной `.torrent`. [S27, S28]

### 6.4. Состояния операции

```text
ANALYZING
  -> PLANNED
  -> PREPARING
  -> DOWNLOADING
  -> VERIFYING
  -> READY_TO_COMMIT
  -> COMMITTING
  -> COMMITTED

При отказе:
  -> PAUSED / NEEDS_ATTENTION
  -> ROLLING_BACK
  -> ROLLED_BACK
```

Repair journal содержит operation id, source/target mappings, ожидаемые file identity и размеры, режим безопасности, подготовленные пути, completed steps и список принадлежащих операции файлов. Он не дублирует каждую запись торрент-resume.

### 6.5. Режим с сохранением исходных данных

По умолчанию для обновления версии:

- Источники только читаются на стадии подготовки.
- Файлы, в которые движок может писать, готовятся в staging.
- Уже правильные данные переносятся в staging обычным копированием либо поддерживаемым copy-on-write clone.
- Обычные hardlinks не использовать для staging изменяемых файлов: запись по одному имени меняет общий файл. [S12]
- На обычном NTFS не обещать доступность универсального reflink. COW clone определяется по конкретной файловой системе/API; ReFS block cloning является отдельным поддерживаемым Windows механизмом. [S29]
- До операции показывать реальную потребность во временном месте. Для огромного изменённого `.pak` она может быть близка к его полному размеру, даже если из сети нужны считаные мегабайты.

Особенность v1: если недостающий piece пересекает границу файлов, staging должен включать **все файлы, в которые запись этого piece может попасть**, даже если большая часть соседнего файла уже правильная. Альтернатива требует отдельного проверенного storage overlay и не вводится молча.

Начальный вариант может готовить полный целевой каталог для максимальной простоты. Оптимизация до staging только write-affected files допускается после теста замыкания по v1-boundary pieces. Это сокращение дисковых затрат, не изменение правил проверки.

Commit начинается после остановки игры/писателей и закрытия конфликтующих handles. Замена набора файлов не объявляется одной атомарной операцией: применяются журналируемые отдельные шаги с возможностью восстановления/отката. Для полного staging directory можно использовать swap каталогов с журналом промежуточного состояния. Для file-level staging нужны backups и replay каждого replace.

### 6.6. Быстрый режим in-place

Отдельный явный выбор: меньше временного места, без обещания сохранения работоспособной старой версии или полного rollback. Подходит для обычного восстановления загрузки, когда пользователь готов заменить содержимое.

Перед началом приложение берёт владение записью, останавливает конфликтующие torrent jobs и предупреждает о завершении сторонних программ, меняющих каталог. Partial progress и resume сохраняются. После сбоя можно продолжить восстановление, но не обещается вернуть старую игру.

Это не скрытый fallback при нехватке диска. Из безопасного режима в in-place переходят только отдельным пользовательским решением.

### 6.7. Truncate, отсутствующие и лишние файлы

`truncate_files` применяется только к правильно отображённым и принадлежащим операции target files при остановленном конфликтующем I/O. Не вызвать библиотечную функцию для произвольного каталога до анализа переименований и ownership. [S01]

После окончания проверяются не только hashes, но и ожидаемая длина каждого выбранного файла. Правильные pieces не доказывают отсутствие лишних байтов за expected EOF.

Отсутствующие файлы докачиваются. Файлы, отсутствующие в новом torrent manifest, не удаляются безусловно: среди них могут быть saves, configs, mods и пользовательские данные. Для явно известных устаревших файлов старого manifest можно предложить отдельное действие с предварительным списком/карантином.

Пути с traversal, неоднозначным case collision, symlink/reparse escape и конфликтующими hardlink aliases требуют отказа или явного безопасного разрешения. Truncate по общему hardlink не должен разрушить другую раздачу.

### 6.8. Владение и параллельность

Один владелец записи для каждой сущности данных. GUI не трогает файлы напрямую. RepairService и libtorrent передают право записи через TorrentLifecycle: остановка job, drain I/O, подтверждение освобождения handles, действие, новая проверка, resume.

Два торрента с пересекающимися файлами не могут одновременно обновлять/усекать их. Импорт из запущенного старого qBittorrent не даёт разрешения qbutt писать в тот же каталог.

## 7. Полезные сопутствующие функции

### 7.1. Политики завершения

Маленький детерминированный rule engine, а не общий язык программирования:

```yaml
# Проектная схема qbutt, не конфигурация существующего qBittorrent.
rules:
  - id: games-remove-job
    match:
      category: games
    on: wanted_files_committed
    actions:
      - remove_torrent
      - notify
```

`remove_torrent` всегда означает удалить задачу и её служебные metadata, сохранив payload. `delete_data` является отдельным действием с явным включением. Не использовать негативную двусмысленную комбинацию нескольких галочек.

Событие возникает после проверки выбранных файлов, завершения переносов/repair commit и завершения необходимых записей, а не при первом отображении 100%. На первом импорте политики запускаются в preview, чтобы не удалить старые задачи массово.

Категории, tags, ratio и время сидирования берутся из существующей модели qBittorrent. Первый совпавший terminal rule завершает обработку; конфликтующие destructive actions проверяются до сохранения. Каждый запуск имеет журнал причины и idempotency key. qbit_manage служит референсом сценариев. [S13]

### 7.2. Диагностика

Панель «Почему медленно» показывает доказательства:

- Сколько кандидатов найдено и из каких разрешённых источников.
- Сколько попыток подключения успешны/отклонены/не завершились.
- Сколько пиров реально передают, сколько держат choke, сколько не имеют нужных blocks.
- Native и remote egress, TCP/UDP inbound отдельно, фактический public endpoint.
- Полезную peer payload скорость, проверенную скорость завершения pieces, relay bytes и wire bytes отдельно.
- Задержки очередей, disk stalls, hash failures, network errors и ограничения скорости.
- Причины выбора маршрута, fallback и запрета маршрута.

Не писать «рои точно виноваты» только потому, что другой торрент быстрый: контроль исключает общий устойчивый потолок тракта, но не все специфические маршруты/протоколы/состояния текущей раздачи.

Логи по умолчанию ограничены размером и временем. Diagnostic export вычищает credentials, passkeys, subscription URLs, приватные каталоги и индивидуальные IP при включённой анонимизации. Полная отладка только отдельным осознанным режимом.

### 7.3. UI и API

Существующий native Qt interface сохраняется. Новые области: Repair preview, Paths, Network diagnostics и Policies. Добавить быстрый поиск/фильтры по категории, состоянию, tracker, пути и источнику данных.

Хэширование, чтение каталога, network probes и большие выборки выполняются не в UI thread. Изменения модели агрегируются. Не переписывать весь UI, чтобы добавить четыре окна.

Существующие API/интеграции сохраняются там, где это дёшево. Новые собственные endpoints выделяются в отдельное versioned пространство и включаются только при разрешённом локальном API. Внутренний path IPC не становится публичным незащищённым WebUI API.

### 7.4. Обновление и восстановление профиля

WinSparkle является стартовым кандидатом для Windows installer. Не реализовывать свои схемы подписи. Обновление должно проверять подлинность пакета и различать «нет новой версии» и «проверка не удалась». [S14]

qbutt.exe, libtorrent внутри сборки и qbutt-net выпускаются согласованным bundle. Не обновлять ядро из случайного upstream URL независимо от приложения. Hello/capability handshake отклоняет несовместимую пару.

До миграции профиля создаётся backup. Binary rollback не считается полноценным rollback, если новая версия уже несовместимо изменила данные профиля. Portable обновление не должно перезаписывать каталог пользовательских данных.

### 7.5. Streaming как отдельное небольшое расширение

Внешний mpv/VLC получает локальный HTTP endpoint с поддержкой Range. Чтение назначает deadlines нужным pieces, а библиотека планирует запросы. Не требуется встроенный player, transcoding или новая реализация sequential scheduling. Endpoint закрыт от чужих клиентов, seek/cancel поддерживает backpressure. [S05, S30]

Делать после файловой и сетевой основы, отдельным PR. Отказ от streaming не должен требовать удаления центральных архитектурных компонентов.

### 7.6. Same-file multi-swarm позже

Пользователь явно добавляет вторую раздачу как источник идентичного файла. Нет автоматического обхода сайтов/трекеров и получения неизвестных torrents. Сначала реализовать reuse уже локально имеющегося одинакового файла. Live merging разных swarm допускается после доказанной идентичности и соблюдения tracker policy, с BiglyBT как референсом. [S09]

## 8. Входящие требования к корректности

1. Любой peer I/O имеет разрешённый PathContext либо явно Native context.
2. Tunnels only не откатывается в DIRECT ни при каком отказе.
3. Смена поколения path инвалидирует зависимые UDP mappings и неподходящие объявления.
4. Один piece picker на torrent обслуживает все его пути.
5. Все принимаемые данные проверяются по целевой torrent metadata; индекс кандидатов не является доказательством.
6. Операция repair не меняет источники в read-only стадии.
7. In-place режим не выдаётся за reversible update.
8. Ни один unknown файл не удаляется как побочный эффект синхронизации.
9. У каждой потенциальной записи есть один владелец, включая пересекающиеся torrent layouts.
10. Лимиты памяти, очередей, сокетов и попыток действуют суммарно.
11. Политика завершения запускается только после готовности данных и commit.
12. Низкая скорость, недоступность и изменение IP не считаются доказательством порчи данных или злонамеренности пира.
13. Координатор не получает ложную «скорость загрузки» от собственного relay loop или повторно посчитанных bytes.
14. Импорт/обновление не изменяет профиль старого qBittorrent и Koala без отдельного действия.

## 9. Испытательный стенд

### 9.1. Наборы данных

Генерируемые фикстуры, а не огромные коммерческие игры:

- v1, v2, hybrid torrents.
- Несколько размеров pieces, последняя неполная piece, пустые файлы и pads.
- Одно изменение блока, append, shrink, лишний хвост.
- Переименование файла/каталога, перестановка файлов, другой piece size.
- Вставка внутри большого файла с ожидаемо низким reuse.
- Повреждение существующего источника после индексации.
- Unicode, длинные пути, регистр, reparse points, hardlinks.
- Недостаток диска, исчезающий том, другой процесс с открытым файлом.
- Перезапуск приложения на каждом шаге commit и rollback.

Torrenttools и существующие libtorrent test facilities использовать для генерации/проверки. [S15, S17]

### 9.2. Сетевая лаборатория

Четыре controlled routes и набор пиров с воспроизводимым seed. Требуются сценарии:

- Один быстрый Native путь; remote не даёт выигрыша.
- Разные пиры достижимы только через разные выходы.
- Один peer доступен везде, но bandwidth/loss различается.
- Ограничение общей последней мили при нескольких быстрых tunnels.
- Choke/un-choke без сетевого отказа.
- TCP работает, UDP заблокирован; IPv4 работает, IPv6 отсутствует.
- Смена IP/UDP mapping, падение qbutt-net, падение edge, reconnect.
- Koala включается/выключается во время активной загрузки.
- Tracker видит правильный исходный адрес; private source restrictions.
- Несколько одинаковых aliases одного VPS не создают swarm amplification.
- Поддельные remote metadata отвергаются до открытия соединения.

Для unit/simulation использовать libtorrent simulation. Для реальных TCP/UDP/QUIC flows использовать Linux namespaces и netem. Toxiproxy удобен для TCP, но не заменяет UDP/QUIC испытания. [S15, S16, S31, S32]

### 9.3. Сравниваемые режимы

1. Контрольный qBittorrent / Native.
2. qbutt / Native.
3. qbutt / лучший отдельный remote edge.
4. Простое распределение соединений без адаптации.
5. qbutt / RouteSelector.

В public swarm отдельная высокая цифра не является результатом. Нужны повторяемые окна, одинаковые ограничения диска/канала и учёт прогрева и изменения состояния роя. Лабораторный тест фиксирует topology и поведение пиров, публичный тест показывает внешнюю применимость, но не заменяет лабораторный.

Метрики: время получения файла, unique verified bytes/sec, network payload/wire overhead, duplicate requests, connection churn, память, CPU, I/O, время UI response и объём дисковой подготовки.

### 9.4. Предлагаемые release gates

Это проектные пороги, не обещания и не результаты измерений:

- Native режим qbutt не хуже контрольного median goodput больше чем на 5% в стабильном стенде; при шуме расширить выборку.
- В контролируемой topology с дополнительными достижимыми быстрыми пирами Mixed получает больше полезных данных, чем лучший отдельный путь, пока не достигнута общая последняя миля.
- В topology без преимущества remote не создаёт значимой постоянной нагрузки/churn и не ухудшает Direct.
- Ноль необъяснённых payload/hash mismatches в тестовом корпусе.
- Ни один packet класса torrent/discovery не уходит Native при Tunnels only.
- Safe repair восстанавливается после каждого injected crash без потери исходных данных; in-place корректно продолжает repair без обещания rollback.
- Delete policies не запускаются до commit и не удаляют payload при `remove_torrent`.
- Pair-version mismatch приложения и ядра приводит к понятному отказу, а не к попытке работать на несовместимом IPC.

## 10. Порядок реализации

| Этап | Результат | Проверка завершения |
|---|---|---|
| A. Baseline и contracts | Сборка upstream, отдельный профиль, pinned зависимости, fixtures, Path/Repair contracts | Артефакт запускается; контрольные download/resume/recheck работают; исходные профили не меняются |
| B1. Repair vertical slice | Read-only preview, managed truncate, in-place recheck, точные длины | Набор grow/shrink/rename/corruption проходит; unknown files сохраняются |
| B2. qbutt-net vertical slice | Отдельное ядро, импорт nodes, закреплённый SOCKS path, telemetry, Koala checks | Один remote путь реально использует нужный egress; профиль Koala нетронут |
| C. Общий multipath TCP | Несколько peer routes в одной session, один picker, общие лимиты | Пиры за разными выходами одновременно кормят одну загрузку без дублирующих клиентов |
| D. Полный сетевой контур | UDP/uTP, DHT, trackers/DNS/webseeds, policy transitions, private handling | Tunnels only действительно закрыт; корректные endpoint identities и capabilities |
| E. Safe update и inbound | Staging/journal/rollback, reverse gateway и внешние проверки | Crash recovery; достижимость реальных TCP/UDP listeners через CGNAT |
| F. Адаптация и продукт | RouteSelector, доказанные метрики, policies, UI, signed update и import/export | Проход release gates; воспроизводимый bundle и диагностический отчёт |
| G. Независимые дополнения | Streaming, расширенный file matching; затем при пользе same-file multi-swarm | Каждая функция имеет отдельные тесты и не усложняет обязательный путь |

B1 и B2 удобно выполнять параллельно после A. Safe update можно вести параллельно сетевым C/D; inbound требует устойчивого path context. Не привязывать план к произвольным «неделям»: прогресс определяется завершёнными проверками и работающими срезами.

## 11. Работа агентами

Четыре независимых направления: application/storage, libtorrent paths, net/edge, UI/integration. У каждого отдельный worktree и маленькие проверяемые PR. Контракты меняются отдельным согласованным PR, а не в четырёх несовместимых реализациях.

До изменения каждого subsystem агент должен перечислить существующие механизмы, которые сохраняются, и показать тест, в котором новой функции ещё нет. После изменения: diff, build, tests, failure cases и сведения о том, что не проверено на реальной сети.

Не начинать с команды «перепиши networking». Начать с команды «сделай два controlled peers, достижимых через разные paths, и заставь одну session скачать от них один torrent с проверенным payload». Следующий этап добавляет реальную сложность только там, где она нужна этому результату.

Использовать долгие автономные серии тестов и fault injection для проверки инвариантов. Количество созданных строк и число агентов не являются метрикой готовности.

## 12. Отложенные гипотезы

**Удалённые BitTorrent workers:** рассматривать, если измерения показывают ограничение именно BitTorrent request pipeline/локальной обработки и relay с настроенными очередями не решает задачу. Тогда потребуется учёт upload fairness, caching, availability, verified delivery, cancellation и отказов. Это отдельный architecture decision, не просто следующий транспорт.

**Publisher-assisted delta:** отдельный формат дополнительных target signatures для подконтрольных раздач. Не обещать тот же выигрыш на произвольных `.torrent` без такого metadata.

**Глобальный piece cache/CAS:** только если metadata-only индекс и reuse существующих файлов дали недостаточный результат на реальных повторных загрузках. Нужно считать saved network bytes против extra disk bytes, hashing cost и recovery complexity.

**Много transport variants одного edge одновременно:** только если один transport ограничивает скорость или устойчивость и эксперимент показывает выигрыш, а не просто создаёт больше competing flows.

## 14. Release checklist

- Известны исходные и пользовательские fork revisions всех компонентов.
- Пройдены capability probes реальных Hysteria2/ShadowQUIC/VLESS сборок.
- Пройдены native, mixed, pinned, tunnels-only и Koala coexistence tests.
- Пройдены repair, crash recovery, policy/delete и resume regression suites.
- Подпись обновления проверяется; mismatch/migration failure имеет понятное восстановление.
- Диагностический экспорт не содержит секретов и персональных сетевых данных без явного выбора.
- Сохранены лицензии, copyright notices и необходимые материалы исходных проектов; перед распространением проверены требования конкретных форков и зависимостей.
- Пользовательская документация не обещает обход любого DPI, ускорение любой раздачи, суммирование четырёх физических каналов или универсальный binary delta.
- Опубликованы измерения и известные ограничения, а не только скриншот максимальной скорости.
